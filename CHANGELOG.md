## [Unreleased]

### Added

- **`REGISTRATION_ENABLED`: close account registration.** Default `true` keeps `POST /auth/register` open; `false` makes it answer `403 registration_disabled` before the body is read, with no password hashing and no rate-limit slot spent. Set it to `false` after creating your own account (`docs/self-hosting.md`). Sign-in, sync and the managed bridge are unaffected; an unparsable value stops startup.
- **Managed bridge re-key: optional `expected_phrase_fingerprint_hex` precondition.** `PUT /managed/accounts/{account_id}/recovery-key` with it replaces the package only while the stored one carries that fingerprint (checked by the writing statement itself); another fingerprint, or no stored package, answers `409 recovery_key_conflict` and writes nothing, so a re-sent older rotation cannot bring a retired recovery phrase back. A retry of a committed re-key (the stored package re-sent) is still the no-op 200, and without the field the replace stays unconditional, so the current ovumcy-managed release keeps working.
- **`PUT /sync/rekey`: store a recovery-key package and the blob sealed under it in one transaction.** Both land or neither does, so a refused blob write no longer leaves a package the stored blob is not sealed under (the old phrase then failed the fingerprint check). The package keeps `PUT /sync/recovery-key`'s step-up rules; the blob keeps `PUT /sync/blob`'s, with `expected_generation` required (`0` = no blob yet). `GET /sync/capabilities` reports `atomic_rekey: true`; the two-call path is unchanged.
- **`PUT /sync/blob`: optional `expected_generation` precondition.** A write that carries it commits only while the stored generation still equals it (checked by the writing statement itself), so a device uploading from a stale baseline gets `409 stale_generation` instead of silently replacing another device's newer blob; a mismatch or no stored blob writes nothing, and a non-positive value answers `400 invalid_blob`. Without the field, writes behave as before.
- **`ALLOWED_HOSTS`: refuse a request for a host the server does not serve.** When set, a request whose `Host` is not listed answers `403 host_not_allowed` ahead of the origin check and every rate limiter, so a page on a domain rebound to the server's address (DNS rebinding) can neither read a response nor spend the victim's per-IP buckets. An IP-literal or `localhost` Host always passes, so the container healthcheck and direct-IP access keep working. Unset, every Host passes as before.
- **Managed bridge: revoke a managed account's sync sessions.** `POST /managed/accounts/{account_id}/sessions/revoke` (behind `MANAGED_BRIDGE_TOKEN`, no request body) deletes every sync session of a managed account, so a session minted before a managed credential change or operator revoke stops working at once instead of living out `SESSION_TTL`. Devices, the encrypted blob, the recovery-key package and the lapse state are kept; the next `POST /managed/session` issues a new session. It answers `200 {"status":"sessions_revoked"}` for an unknown account, one with no sessions, and a self-hosted account whose id matches alike, never touches a self-hosted account, and is safe to repeat.

- **Managed bridge: re-key a managed account's recovery phrase.** `PUT /managed/accounts/{account_id}/recovery-key` (behind `MANAGED_BRIDGE_TOKEN`) replaces a managed account's wrapped recovery-key package, or stores a first one, with the same validation as `PUT /sync/recovery-key`. ovumcy-managed calls it after re-authenticating the owner, because a managed session can store only a first package. It answers `200 {"status":"recovery_key_replaced"}`. Sessions, devices and the encrypted blob are kept. An unknown account and a self-hosted account whose id matches both answer 404 `managed_account_not_found`, and nothing is written.

- **Optional per-run cap on the lapsed-account sweep, and an abort on repeated delete failures.** `LAPSED_ACCOUNT_SWEEP_MAX_DELETES` (and `purge-lapsed-accounts -max-deletes N`) stops a run after erasing N accounts, so a host clock that jumps past the grace period no longer erases every in-grace lapsed account in one run; a capped run is logged and the CLI prints `lapsed_account_sweep_capped=true`. The default, `0`, stays unbounded. Independently, a run now ends after five delete failures in a row instead of walking every candidate against a faulty database; the candidates stay eligible for the next run.

### Changed

- **`POST /auth/totp/verify`: a pending secret discarded at its lifetime cap answers `409 totp_enrollment_expired`** (formerly `429 rate_limited` with `Retry-After: 1`), so a client restarts enrollment instead of waiting; the route limiter and the rolling TOTP budget keep `429 rate_limited`. Allowed-origin responses now carry `Access-Control-Expose-Headers: Retry-After`, so a browser client can read the wait.
- **A failed `last_seen_at` update no longer fails the request.** When recording a session's last use fails (a busy or read-only database), an authenticated request now proceeds and only the error's type is logged, instead of answering 500 on every authenticated route. A session revoked between lookup and update still answers 401.
- **Recovery-key writes require a wrapped master key of exactly 96 hex characters.** `PUT /sync/recovery-key` and the bridge re-key `PUT /managed/accounts/{account_id}/recovery-key` now refuse any other length (formerly: at least 64, even) with `400 invalid_recovery_package`; 96 is what the app sends (a 32-byte key plus its 16-byte tag). A package already stored under the old rule is untouched: it still reads, and its identical re-put on `PUT /sync/recovery-key` still returns it.

- **Blob transfers are processed at most 4 at a time.** `PUT /sync/blob` and `GET /sync/blob` now share a server-wide limit of 4 transfers holding a blob in memory; a further transfer waits for a free slot within its HTTP read/write timeout, with no new status code. A max-size upload needs about 7× `MAX_BLOB_BYTES` of memory, so blob work stays near 28× `MAX_BLOB_BYTES` (about 450 MiB at the default) however many sessions upload at once.

- **Image tags: only main moves the `main` tag, only the highest release moves `latest` and `X.Y`.** A manual run on another branch no longer writes a branch tag, and a release tag pushed on an older commit no longer moves `latest` or its `X.Y` tag backwards. The documented cosign identity now pins the workflow to `refs/heads/main` and `refs/tags/v*`.

- **Account erase truncates the WAL, registration is one transaction, `file:` database paths are created owner-only.** After an account erase the server checkpoints and truncates the `-wal` file (best effort, never fails the erase); registration stores the account and its first session atomically; a missing database behind a `file:` path is pre-created 0600 like a plain path.

- **Breaking for operators: the credential routes default to 5 requests per 15 minutes, and the sync routes have their own limit.** `AUTH_RATE_LIMIT_COUNT` / `AUTH_RATE_LIMIT_WINDOW` now default to `5` / `15m` (was `10` / `1m`), which caps password guessing against one login at about 480 a day instead of 14,400. They meter registration, login (per IP and per login), forgot/reset password, the TOTP challenge, logout, password change, recovery-code regeneration, TOTP enroll/verify/disable, account deletion and the shared step-up bucket; a 429 there carries a `Retry-After` of up to 900 seconds. A login that issues a session and a logout that finds one now give their per-IP slot back, so only failures spend those budgets and sign-ins behind one address do not lock each other out. The `/sync/devices`, `/sync/recovery-key` and `/sync/blob` routes move to the new `SYNC_RATE_LIMIT_COUNT` / `SYNC_RATE_LIMIT_WINDOW` (default `10` / `1m`, the old figures), and the 30× read-state budget (`GET /auth/session`, `GET /sync/capabilities`, `GET /sync/devices`) now derives from `SYNC_RATE_LIMIT_COUNT`, so sync traffic is unchanged. An operator who set `AUTH_RATE_LIMIT_*` to loosen sync throttling should set `SYNC_RATE_LIMIT_*` instead, and one whose environment pins the old `10` / `1m` explicitly keeps the old ceiling until those lines are removed.

- **`Retry-After` on a per-IP or per-account rate-limit 429 follows the limiter's window.** The header was always `60`; it is now the seconds left in the spent window (rounded up, at least 1): at most `900` on the credential routes and `60` on the sync and read-state routes with the defaults, and it no longer understates a longer configured window.

- **API description aligned with the code (documentation only; no status code, error key, header or field changes).** `openapi.yaml` now states that `DELETE /account` is not idempotent for the same token (a retry answers 401), documents the request-body caps and `400 invalid_json` on every body-taking route, the 415 content-type gate, the plain-text 404/405 and bare 204 `OPTIONS` answers, that `/metrics` always needs its bearer token, the `Retry-After` range on 429 (60, or 1 to 900 on a TOTP budget; a spent enrollment lifetime budget carries `1` but needs a restart), the empty session fields on a TOTP login challenge, and that the bridge lapse route answers `lapse_recorded` as a no-op for an absent account. The entries below that described managed accounts as exempt from the password step-ups or the TOTP window as 10 attempts are corrected.

- **Startup now refuses a malformed `ALLOWED_ORIGINS` entry and a shared bridge/metrics token.** Every `ALLOWED_ORIGINS` entry must be exactly `scheme://host[:port]` with an http or https scheme; `null`, `*`, wildcards, a path (including a trailing `/`), a query, a fragment or userinfo stop startup: `null` would admit every sandboxed or `file:` origin, and the rest can never match a real `Origin`. `MANAGED_BRIDGE_TOKEN` and `METRICS_BEARER_TOKEN` must differ once trimmed (the error prints neither). An all-zero `FIELD_ENCRYPTION_KEY` is still accepted, with a startup warning: replace it with a real key (`openssl rand -hex 32`) before enrolling TOTP.

- **A cross-site request without an `Origin` header is refused by its fetch metadata.** A cross-site no-cors `GET` (an `<img>` or `<script>` tag pointing at the server) sends no `Origin`, so it passed the origin gate and spent the victim's per-IP session-lookup bucket. A request without `Origin` whose `Sec-Fetch-Site` is `cross-site` or `same-site` now answers 403 `origin_not_allowed` before any rate limiter. Browsers send `Sec-Fetch-Site` only over HTTPS or to localhost, so a server reached over plain HTTP keeps the old exposure. `/healthz`, `/readyz` and `/metrics` are exempt; requests with neither header (native apps, bridge calls, probes) are unaffected.

- **Account deletion refuses a managed account in the service, not only at the transport.** A managed account has no password, so the step-up behind `DELETE /account` passed it and only the transport refused it. That step-up now refuses a managed account, so `AuthService.DeleteAccount` refuses it too (the route still answers 403 `managed_account_delete_via_bridge`), and a managed session's first `PUT /sync/recovery-key` is handled before the step-up, so it no longer draws on (or waits for) the account's step-up bucket.

- **The bridge purge and premium signal answer a self-hosted account's id like an unknown one.** `DELETE /managed/accounts/{account_id}` and `POST /managed/accounts/{account_id}/premium` answered 400 `invalid_managed_account` when the id belonged to a self-hosted account, which told the bridge caller that account existed. Both now answer the same 200 an unknown id gets, as `sessions/revoke` already did, and still leave the self-hosted account untouched. On these two routes 400 `invalid_managed_account` now means only that the id fails the managed-account id pattern. `POST /managed/session` still refuses a self-hosted id with 400, since it cannot issue a session for it.

- **Breaking for managed clients: a managed session can no longer replace the wrapped recovery key.** A managed account has no password, so `PUT /sync/recovery-key` skipped the step-up for it and a stolen managed session could swap out the owner's recovery path. A managed session now stores only a first package; a valid package that differs from the stored one answers 403 `managed_recovery_key_overwrite` and writes nothing. Re-putting the stored package still answers 200. Client note: a managed client cannot rotate its recovery phrase through a session; ovumcy-managed re-keys it through `PUT /managed/accounts/{account_id}/recovery-key`, and the bridge purge clears the package with the rest of the account.

- **Breaking for browser clients: a request from an origin not in `ALLOWED_ORIGINS` is refused on every method, not only on preflight.** It answers 403 `origin_not_allowed` before any rate limiter, so a cross-site page sending a body-less no-cors `POST /auth/login` (which needs no preflight and passed the content-type check) can no longer spend a victim's per-IP login bucket. Requests without an `Origin` header — the native apps, ovumcy-managed's bridge calls, health probes — are unaffected. Client note: a web client served from the server's own origin must list that origin in `ALLOWED_ORIGINS`, since browsers send `Origin` on same-origin `POST`, `PUT` and `DELETE`.

- **The lapsed-account sweep page size has a floor of 100.** Listing one page of candidates reads the whole `accounts` table, so `LAPSED_ACCOUNT_SWEEP_LIMIT=1` (or `purge-lapsed-accounts -limit 1`) cost one full scan per eligible account. A value from 1 to 99 now means 100; `0` still uses the store default (500).

- **Breaking for clients: request bodies must be declared `application/json`, and login, device id and label have maximum lengths.** A request with a body and any other (or no) `Content-Type` now answers 415 `unsupported_media_type`, before any rate limiter — a cross-site page could otherwise POST `text/plain` without a CORS preflight and spend a victim's per-IP auth bucket. Requests without a body (logout, a session-only device removal), including a chunked body of zero bytes, need no content type. Registration rejects a login over 254 bytes (400 `invalid_registration_input`), and device attach rejects an id over 128 bytes or a label over 64 (400 `invalid_device`). Existing accounts still sign in and existing devices can still be removed, because login and removal do not re-check the lengths. Re-attaching a device stored with a longer id or label is refused. Client note: send `Content-Type: application/json` on every request that carries a body, and keep device labels to 64 bytes.

### Fixed

- **An empty `current_password` no longer spends a step-up attempt.** Every step-up route (change password, regenerate recovery code, TOTP enroll and disable, `DELETE /account`, `PUT /sync/recovery-key`, enrolled device removal) still answers 401 `invalid_current_password` for a missing password, but now refuses it before hashing and gives the shared per-account step-up slot back, so a client that sends no password first cannot lock the owner out. A wrong non-empty password stays charged. A device removal checked as "no TOTP" that finds an enrollment committed meanwhile is refused instead of comparing the password uncharged.
- **Two-factor sign-ins behind one address no longer lock `/auth/login`.** A login that answers with a TOTP challenge now gives its per-IP slot back, and so does a completed `POST /auth/totp/challenge`, so five MFA sign-ins behind one NAT no longer spend the 5-per-15-minutes per-IP budget. Wrong passwords and wrong codes stay charged, and the per-login slot and the TOTP code budgets are unchanged.
- **A clock step back no longer refills a pending TOTP enrollment's guesses.** The 10-guess lifetime budget of a pending enrollment secret restarted its count when the server clock stepped back behind its first guess, granting 10 more guesses at the secret; the count is now kept, and only a new enrollment start clears it.
- **Step-up writes hold the TOTP state they were checked under.** `DELETE /account`, `PUT /sync/recovery-key` and `DELETE /sync/devices/{device_id}` now refuse with 401 `invalid_current_password` when the session's own TOTP enrollment commits while the request is being checked, instead of completing with the password alone (or, for a device, with the session alone). A device removal on an enrolled account also refuses when the password changed meanwhile. Nothing is erased, written or removed; a retry carries the step-up the account now requires (password and code).
- **One live TOTP login challenge per account, and no password hashing for a dead reset token.** Issuing a login challenge now replaces the earlier ones in the same transaction as the insert, so concurrent logins cannot leave two live challenges. `POST /auth/reset-password` checks the reset token read-only first and answers `invalid_reset_token` for an unknown, used or expired one before hashing the new password and recovery code; the answer depends on the token only, never on a login.
- **Early refusals are rate-limited.** TOTP enroll, verify and disable answered `503 totp_not_configured`, and the device, recovery-key and blob routes answered `403 sync_disabled`, before charging their per-account limiter; each now charges it first, so a session cannot loop on those answers unmetered.
- **Re-attaching a device returns its original `created_at`.** `POST /sync/devices` for a device the account already owns answered `created_at` as the time of the request, while the stored row kept the first attach time; it now answers the stored value.

- **TOTP account-state refusals are 409, not 503.** `POST /auth/totp/disable` on an account without TOTP — including the loser of two concurrent disables — now answers `409 totp_not_enabled` (once the winning disable has committed, the loser's code spends no step-up TOTP attempt), and `POST /auth/totp/verify` with no pending secret answers `409 totp_enrollment_not_started`. Both used to answer `503 totp_not_configured`, which now means only a server without `FIELD_ENCRYPTION_KEY`. **Client change:** treat `totp_not_enabled` as "already off" and `totp_enrollment_not_started` as "restart enrollment".

- **The lapsed-account sweep drains every eligible account per run.** A run erased at most one page (`LAPSED_ACCOUNT_SWEEP_LIMIT` or `purge-lapsed-accounts -limit`, default 500) of accounts past their grace period, so more lapses than that waited one interval per page. Each run now pages through every eligible account, in lapse order with a cursor that never lists a skipped account twice. **Operator change:** `LAPSED_ACCOUNT_SWEEP_LIMIT` and `-limit N` are now the page size, not a cap on how many accounts one run deletes, and `-dry-run` reports the full eligible count. Eligibility is unchanged: a signalled lapse older than the grace period, re-checked inside each delete.

- **The expired-rows sweep drains its backlog.** A run deleted at most one batch (`EXPIRED_ROWS_SWEEP_LIMIT`, default 500) per table per interval, so a server that issued more expired sessions, reset tokens or TOTP challenges per day than that never caught up. Each run now repeats the batch per table until a short one comes back; `EXPIRED_ROWS_SWEEP_LIMIT` is the batch size, and the connection is free for requests between batches.

- **A password change now rotates the recovery code.** Changing the password left the old recovery code valid, so a code noted down before a suspected compromise still reset the account afterwards. `POST /auth/change-password` now replaces the recovery code in the same transaction that sets the new password, and only while both the password and the recovery code are still the ones it read (a reset, regeneration or TOTP enable landing meanwhile answers `invalid_current_password`). Because the new code can reset the password and clear TOTP, a TOTP-enrolled account must now also send a current `code`, checked like `POST /auth/recovery-code/regenerate` (missing or wrong → 401 `totp_invalid_code`; counted in the per-account TOTP window; 503 `totp_not_configured` without `FIELD_ENCRYPTION_KEY`). **Client change:** the response now carries `recovery_code` next to `status`; the app must show it — the previous code stops working. On an enrolled account the app must collect a TOTP code before submitting the change.

- **One device per session.** A session binds to the first device it attaches; a later `POST /sync/devices` naming a different device used to answer 200, upserting that device while the session stayed bound to the first, so removing the second device left the session alive. That attach now answers `409 session_device_bound` and creates or refreshes nothing; re-attaching the session's own device still answers 200. The bound-device check and the attach commit in one transaction, so concurrent attaches from one session cannot bind two devices. **Client change:** a client that switches device identity must log in again for the new device instead of reusing its session; `session_device_bound` is the signal to do so.

- **Hardened reference edge and bridge token.** `docker-compose.caddy.yml` no longer defaults `SYNC_SITE_ADDRESS` to `:80`, which served plain HTTP; the stack now refuses to start until it names the public hostname, so Caddy serves HTTPS. The Caddy, nginx and Traefik examples answer `/managed/*` with `403` at the public edge, as they already did for `/metrics` — the managed bridge's one caller reaches the service over the private network. A set `MANAGED_BRIDGE_TOKEN` shorter than 32 bytes is now a startup error: the bridge routes are not rate-limited, so the token alone must resist guessing. **Upgrade:** set `SYNC_SITE_ADDRESS` before `docker compose up` with the Caddy example, and regenerate a short bridge token with `openssl rand -hex 32`.

- **Breaking for TOTP-enrolled accounts: account deletion, the recovery-key overwrite and device removal need a current TOTP code.** A session plus the password was enough to erase the account or overwrite the wrapped recovery key, and a session alone was enough to remove the owner's devices (revoking their sessions). On an account with TOTP enabled, `DELETE /account` and `PUT /sync/recovery-key` now also require a current `code`, and `DELETE /sync/devices/{device_id}` requires a JSON body with `current_password` and `code` (the password is checked first, and wrong passwords draw on the shared step-up bucket). The code is checked like `POST /auth/change-password`: missing or wrong → 401 `totp_invalid_code` and nothing changes, a replayed code → 401 `totp_replayed`, each code is single-use across every TOTP route and counted in the per-account TOTP window (a missing code is not), and 503 `totp_not_configured` without `FIELD_ENCRYPTION_KEY`. Device removal on an account already deleted now answers 401 `unauthorized` instead of 404. Accounts without TOTP are unaffected: they still remove a device with no body, and that removal does not touch the step-up bucket. **Client change:** on an enrolled account the app must collect a TOTP code for account deletion and the recovery-key overwrite, and the password plus a TOTP code before removing a device; a wrong code now also spends the account's step-up TOTP budget, so five wrong codes on these routes lock those code checks until the window ends (the sign-in budget is separate).

- **Re-putting the stored recovery-key package needs no step-up.** Clients send the wrapped recovery key with every upload, without a password, so after the step-up requirement each upload's re-put answered 401. A `PUT /sync/recovery-key` whose package equals the stored one — after the same normalization (trimmed, lowercased fields) and with the same `mnemonic_word_count` — now answers 200 with the stored package, needs neither `current_password` nor `code`, writes nothing (`updated_at` stays), and is answered even while the shared wrong-password bucket is spent. Any other package is still an overwrite behind the password and, on a TOTP-enrolled account, a current code; a managed session cannot replace a different package at all (403 `managed_recovery_key_overwrite`; only the bridge re-key route can). **Client change:** a client may keep re-putting an unchanged package without credentials; replacing it (a new phrase) on a self-hosted account must send `current_password`, plus `code` when TOTP is enabled.

- **Breaking: `DELETE /account` and `PUT /sync/recovery-key` require the current password.** A session token lives for 30 days by default, and with it alone anyone could erase the account or overwrite the wrapped recovery key that is the owner's only way back to their data. Both requests now carry `current_password` in the JSON body and get `401 invalid_current_password` when it is wrong; `DELETE /account` therefore needs a body. Managed accounts have no password, so a managed session is refused instead: `DELETE /account` answers it 403 `managed_account_delete_via_bridge` before reading the body, and `PUT /sync/recovery-key` refuses a differing package with 403 `managed_recovery_key_overwrite`.

- **A blob generation may run at most 15 minutes ahead of server time.** v0.3.0 accepted any generation up to `MaxInt64 − 2^32`; the bound now moves with the clock, so a write parked at the ceiling by a session that is later revoked keeps the owner's writes stale for at most 15 minutes. Fifteen minutes still covers real device clock drift; a device whose clock is further ahead gets `invalid_blob` until it is corrected.

- **A blob generation stored above the bound before the upgrade no longer strands the blob.** A v0.3.0 install can hold a generation far beyond now + 15 minutes, which every later write failed to beat: the bound refused anything higher and the stale check anything lower. While the stored generation is above the current bound, the next valid `PUT /sync/blob` replaces the whole blob even with a lower generation; once replaced, the stale check governs it again. The stored row is never rewritten in place, because clients seal the generation into the ciphertext and an edited generation would no longer decrypt. **Client note:** a device that already opened such a blob holds its generation as the restore rollback floor and treats the replacement as a rollback until that floor is reset.

- **Go 1.27.** The Go directive moves to 1.27.4 and the build image to `golang:1.27-bookworm`; CI's golangci-lint pin moves to v2.15.0 to analyse the 1.27 toolchain. A source build now needs Go 1.27.4 or later.

- **`GET /readyz` is schema-aware.** Readiness now applies the same applied-migration name-set comparison that gates startup, so a still-running `serve` whose volume a newer image has migrated turns not-ready instead of continuing to look serviceable — the running-process half of the refusal that already stopped a downgraded binary from booting (see [docs/self-hosting.md](docs/self-hosting.md#upgrading-and-rolling-back)). Operator-visible consequence: a container can now go `unhealthy` for a reason other than the process being gone, and an orchestrator configured to act on health will act on it. The probe stays two small statements — a `sqlite_master` lookup and the `schema_migrations` name set — so polling it on the healthcheck interval costs nothing measurable.

- **A non-ASCII managed-account id could name an ASCII account on the bridge.** Every bridge route lowercased the id before checking it against `^[a-z0-9][a-z0-9_-]{7,127}$`, and lowercasing folds U+212A KELVIN SIGN into `k`, so `Kelvin-acct` reached `kelvin-acct`; trimming Unicode spaces (U+00A0, U+3000) did the same for a padded id. The id, trimmed of ASCII whitespace only, is now checked against the ASCII pattern (either case) first and lowercased after; a non-ASCII id answers 400 `invalid_managed_account` on every bridge route. An upper-case ASCII id still names its lowercase account.

- **Each page of the lapsed-account sweep scanned and sorted the whole `accounts` table.** Migration `0013` adds a partial index on `(julianday(lapsed_at), id)` covering lapsed accounts only, and the sweep now reads each page of candidates through it in order and stops at the page size. On a self-hosted install no account is lapsed, so the index stays empty.

- **The container healthcheck failed for `BIND_ADDR=[::]:<port>` on hosts with `net.ipv6.bindv6only=1`.** It probed `127.0.0.1`, where an IPv6-only wildcard bind does not answer. A `[::]` bind is now probed on `127.0.0.1` and, when that cannot connect, on `::1`; `:<port>` and `0.0.0.0:<port>` still probe `127.0.0.1` only. Concurrent `/readyz` probes also share one database check even when the probe that started it gives up, and each probe stops waiting at its own deadline.

- **The expired-rows sweep scanned whole tables on every batch.** Each batch of the sessions, password-reset-token and TOTP-challenge sweep re-ran an unindexed `julianday(expires_at)` lookup, so a backlog of N rows cost about N/limit full scans per run while holding the database's single connection. Migration `0012` adds an index on that exact expression to each of the three tables, and the sweep now finds its batch through it. The index is built once when `migrate` runs; on a large database that step takes a little longer.

- **Two `migrate` runs started at once could fail one of them.** Each run read the list of pending migrations once, before taking the write lock, so a second `migrate` (or a `migrate` racing a newer build's) tried a version the first had just applied and failed on its DDL. Nothing was corrupted, since that migration's transaction rolled back, but the run exited non-zero. Each migration now re-checks inside its own transaction whether it is already recorded and skips it if so.

- **`migrate` gave up after 30 seconds.** The whole run shared one 30 s deadline, so building migration `0012`'s indexes over a large table could be cut short, and `migrate` exited non-zero with that migration rolled back. `migrate` now has no time limit; Ctrl-C or SIGTERM stops it, rolling back only the migration in progress. Run one `migrate` at a time. A second run that waits more than 5 s for the first one's lock still exits with `database is locked` and is safe to run again.

- **A `DB_PATH` with its own `_txlock` silently undid the write-lock-at-begin setting.** The SQLite driver uses the first `_txlock` in the connection string, and the path's query comes first. A path such as `/data/sync.sqlite?_txlock=deferred` brought back the `SQLITE_BUSY_SNAPSHOT` failures that `_txlock=immediate` prevents. `serve`, `migrate` and `purge-lapsed-accounts` now refuse such a path when they open the database. Other query parameters are kept.

- **`docker compose stop` could kill the server mid-drain.** The server waits up to 10 s for in-flight requests and then stops its sweeps, which is exactly Docker's default stop grace. The bundled compose file now sets `stop_grace_period: 30s`, and a drain that times out is logged rather than dropped silently. If you run the image another way, give it at least 30 s between SIGTERM and SIGKILL.

- **The server's `/tmp` had no size limit.** It is a RAM-backed tmpfs, and an uncapped one may grow to half the host's memory if SQLite spills a large temporary file there. The bundled compose file now caps it at 64 MiB, so a runaway spill fails that statement with `SQLITE_FULL` instead of using up host memory. Normal operation uses a small fraction of that.

- **Rows with an unreadable expiry were never swept.** A session, reset token or TOTP challenge whose stored `expires_at` SQLite cannot read as a date could not be used (its lookup failed), but the expired-rows sweep skipped it, so it stayed in the database forever. The sweep now removes it. The managed-bridge purge also checks `mode = 'managed'` in the delete statement itself, and a new sync blob's `created_at` is written in the same RFC 3339 format as every other timestamp.

- **`latest` image tag followed every commit to main.** A self-hoster pulling `latest` could receive forward-only migrations no release had announced, and two publish runs could interleave their tag writes. `latest` now moves only on a `vX.Y.Z` release tag (never a pre-release), releases also get `X.Y.Z` and `X.Y` tags, main builds keep the `main` tag, and publish runs for one ref queue instead of overlapping.

- **A flood of `/readyz` probes could queue every request behind it.** `/readyz` is public and exempt from rate limits, and each probe ran two schema queries on the store's single connection. One readiness answer is now reused for one second, and concurrent probes share the check in flight, so probes cost at most one check per second however fast they arrive. Closing the store drops the cached answer.

- **A password holder could lock the owner out of every TOTP step-up.** One per-account window of 10 code attempts per 15 minutes served the login challenge and every session-authenticated code check, so whoever held the password could keep it spent through login challenges and block the owner's password change, device removal, TOTP disable, account deletion and recovery-key overwrite. Code attempts now draw three separate budgets — sign-in challenge, enrollment verify, in-session step-up — each 5 per 15 minutes, keyed by client address and by account and refused (429 `rate_limited`, `Retry-After`) when either is spent. A sign-in success clears only the caller's client bucket; an in-session success clears both. Enrollment verify now also draws its own rolling budget beside the per-pending-secret cap. The budgets live in memory and reset on restart.

- **A refunded rate-limit slot could land in the next window.** A slot reserved just before a window ended and refunded after the next one opened lowered the new window's count, granting an extra attempt. A refund now returns the slot only to the window it was reserved in.

- **The container healthcheck ignored the host in `BIND_ADDR`.** The probe always called `127.0.0.1`, so a server bound to one specific address (`BIND_ADDR=10.0.0.5:8080`) was reported unhealthy while it served normally. The probe now calls the address the server listens on, and loopback only when `BIND_ADDR` names every interface (empty host, `0.0.0.0` or `::`).

- **Lapsed accounts behind rows that cannot be deleted were never erased.** The lapsed-account sweep ended a run after five delete failures in a row and every run restarted at the same head, so five rows failing permanently (a constraint or a corrupt row) shielded every later account. A row-specific failure (a constraint, a datatype mismatch, a value too big) is now reported and skipped, and the run continues; every other failure still counts toward the abort.

- **Expiry checks misordered instants within one second.** Stored timestamps are RFC3339Nano, which drops trailing zeros, and SQL compared them as text, so `…:05Z` sorted after `…:05.5Z`. A reset token could still be claimed for up to a second after it expired, and the expired-row and lapsed-account sweeps could skip a row for that second. Every instant compare in SQL now goes through `julianday()`.

- **A write could fail with 500 while `migrate`, `purge-lapsed-accounts` or a backup ran.** A transaction that read and then wrote, while a second process on the same database committed in between, failed with `SQLITE_BUSY_SNAPSHOT`, which the busy timeout cannot wait out. Every transaction now begins with `BEGIN IMMEDIATE` and waits for the write lock at its start.

- **SIGTERM closed the database under live requests.** `serve` returned as soon as graceful shutdown began, so the database closed while in-flight handlers were still running; a password change or reset caught mid-way could commit its new hash and fail to revoke the old sessions. `serve` now waits for the HTTP drain (up to 10 s) and for the in-process sweeps to stop before closing the database.

- **A stolen session could guess the password once per step-up route.** Change-password, recovery-code regeneration, TOTP enroll and disable, `DELETE /account` and `PUT /sync/recovery-key` each had only their own per-account bucket, so a session holder got `AUTH_RATE_LIMIT_COUNT` wrong passwords per window on every one of them. Wrong current passwords now share one per-account bucket across all six routes; once it is spent they answer 429 `rate_limited` until the window ends. A correct password, or any other refusal, does not count.

- **Account deletion and the recovery-key overwrite ran on a stale password check.** `DELETE /account` and `PUT /sync/recovery-key` verified the current password, then erased or wrote in a separate step, so a password change or reset landing during the check — or a revocation of the caller's session — did not stop them. Both now commit in one transaction only while the password hash is still the one verified (otherwise 401 `invalid_current_password`) and the caller's session still exists (otherwise 401 `unauthorized`).

- **Reverse-proxy examples left side doors open.** Under `docker-compose.caddy.yml` the app still published `127.0.0.1:8080`, so anything on the host reached it around Caddy's `/metrics` and `/managed/*` block; the Caddy and Traefik overrides now drop that mapping (`ports: !reset []`, Docker Compose 2.24.4 or newer). The Traefik example trusted its whole Docker subnet, so any container on it could pick its own rate-limit key; Traefik is now pinned to `SYNC_PROXY_IP` (default `172.30.98.10`) on its own `edge` network and only that address is trusted — `TRUSTED_PROXY_CIDRS` no longer needs to be exported for it.

- **Compose containers ran with default privileges and floating images.** The app, the one-shot `init-data-perms` step, Caddy and the Traefik example now run with a read-only root filesystem, all capabilities dropped (the proxies keep `NET_BIND_SERVICE`; `init-data-perms` keeps `CHOWN` and `DAC_OVERRIDE`) and `no-new-privileges`. `busybox`, `caddy` and `traefik` are pinned by digest, and Dependabot now updates them. The Traefik example reads its routes from `dynamic.yml` through the file provider and no longer mounts the Docker socket. **Upgrade note:** an override that writes outside `/data` in the app container now needs its own `tmpfs` or volume.

- **Config accepted values that weaken their own protection.** `METRICS_BEARER_TOKEN` had no minimum length although `/metrics` is not rate-limited; it now needs at least 32 bytes, like `MANAGED_BRIDGE_TOKEN`. `TRUSTED_PROXY_CIDRS` accepted any IPv4 /8, including public ones, and `172.16.0.0/8` (which masks to the public `172.0.0.0/8`); a public IPv4 range must now be /12 or narrower, while private, loopback, CGNAT and link-local ranges may be as wide as the range itself. `LAPSED_ACCOUNT_GRACE_PERIOD` accepted any positive duration, so `60m` typed for 60 days erased a lapsed account within a sweep; it must now be at least `24h`. **Upgrade note:** a deployment with a shorter metrics token, a public range wider than /12, or a grace period under a day now fails at startup with an error naming the variable.

- **An empty bridge premium body recorded a lapse.** `POST /managed/accounts/{account_id}/premium` read a missing `active` as `false`, so `{}` or `null` revoked the account's sessions and started its purge clock. `active` is now required; a body without it answers `400 invalid_entitlement_signal` and changes nothing. ovumcy-managed always sends it.

- **HTTP-layer hardening.** `DELETE /auth/session` answered 401 on a store failure, telling the client its session was gone while it stayed live; it is now `500 internal_error`. A session over its per-account budget got every session lookup refunded at the per-IP gate; a handler's 429 now keeps that slot charged. The login-identifier bucket key is a SHA-256 of the normalized login, so it has a fixed size instead of up to 4 KB. The log sanitizer also strips U+2028/U+2029, which JSON and JavaScript log viewers treat as line breaks.

- **A TOTP disable could land on top of a password change, or half-apply.** Disable verified the password and code, then cleared the secret and deleted challenges and sessions in separate statements. A disable verified against the old password could land after a password change or reset, and a failed cleanup left TOTP off with sessions or challenges behind. `POST /auth/totp/disable` now commits in one transaction, only while the password hash and TOTP secret are still the ones it verified; a password moved meanwhile answers `invalid_current_password`, a factor disabled or re-enrolled meanwhile `totp_replayed` (or `totp_not_configured` / `totp_invalid_code` when it lands after the code's step was claimed), and a failure changes nothing.

- **A recovery code from before TOTP enrollment could still remove TOTP.** Enrolling left the existing recovery code valid, and a reset with it clears TOTP — so whoever held the password and a code issued before enrollment could strip the second factor without ever presenting it. `POST /auth/totp/verify` now rotates the recovery code in the same transaction that enables TOTP, deletes pending reset tokens and revokes other sessions; the previous code stops working. Because verify now hands out a recovery code, each pending secret now gets 10 verify attempts in total; the 11th answers 429 and discards the pending secret — restart with `POST /auth/totp/enroll`. Recovery-code regeneration and enrollment start no longer overwrite a concurrent TOTP enable: regeneration writes only while the code it read is current, and a start leaves an enabled account alone. **Client change:** the verify response now carries `recovery_code` next to `status`, and the app must show it to the user — it is the only working recovery code from that point on.

- **A password change could overwrite a reset, or outlive its own session.** Password change verified the current password, then wrote the new hash unconditionally and cleaned up sessions, challenges and reset tokens in separate statements. A change verified against the old password could land after the owner's reset; a change whose session was revoked meanwhile (by a TOTP enrollment, say) still set the password and then deleted the owner's sessions; and a failed cleanup left the new password beside surviving sessions. The change now commits in one transaction, only while the stored hash is still the one verified (otherwise `invalid_current_password`) and the caller's session still exists (otherwise 401); a failure changes nothing.

- **A TOTP code verified before a disable could still be spent after it.** The step claim checked only that the step was new; a disable resets the step and a re-enroll swaps the secret, so a request that verified a code against the old secret could still claim its step and finish (a recovery-code regeneration into a session the disable had just revoked, say). The claim now also requires the stored secret to be the one the code was verified against; a request that loses this race answers 401 `totp_replayed`, including an enrollment completion whose pending secret was replaced by a restart (previously `totp_invalid_code`).

- **`purge-lapsed-accounts dry-run` deleted for real.** Flag parsing stopped at the first non-flag argument, so `dry-run` without its dash was ignored and the purge ran. Any positional argument is now refused before the database is opened.

- **A login racing a password change could keep a session.** Login checked the password, then minted a session or TOTP challenge in a separate step; a change or reset landing in between revoked the sessions that existed, and the new one survived. A login racing a TOTP enrollment could likewise get a password-only session. Sessions and challenges are now inserted only while the password hash and TOTP state are still the ones the login verified; otherwise the login verifies once more against the current account, so the old password after a change answers `invalid_credentials` and a fresh enrollment yields a challenge. Completing a TOTP challenge now consumes it in the same transaction that creates the session, so one challenge yields at most one session. TOTP disable now revokes sessions even when its challenge cleanup fails.

- **A write could outlive the revocation of its own session.** The session was checked when a request arrived, but the write ran only after the body was read, so a session revoked in between (by a password change or reset, a TOTP change, or a device removal) still regenerated the recovery code, started or completed a TOTP enrollment, attached or removed a device, or uploaded the blob. Each of these now commits only while the caller's session still exists, checked in the write's own transaction; otherwise it answers 401 `unauthorized` and writes nothing.

- **SQLite storage hardening.** Deleted rows (an erased account's ciphertext and hashes) could survive as free pages in the database file and in any copy of it; every connection now runs with `secure_delete`, which zeroes freed pages. A new database file was created under the process umask (often 0644) and its `-wal`/`-shm` files followed; it is now created 0600 before SQLite opens it. An existing file keeps its mode — tighten it with `chmod 600` on the database and its `-wal`/`-shm` files. `DB_PATH=:memory:` silently lost all data, schema included, when the pool retired its connection after 30 minutes; an in-memory database's connection is now kept for the life of the process.

- **A failed password reset could lose the new recovery code.** Reset rotated the password and recovery code, then cleared TOTP and deleted sessions, challenges and reset tokens in separate statements. A failure after the rotation answered 500: the new recovery code was never shown while the old one no longer worked, and sessions could outlive the reset. All of it now commits in one transaction; a failure changes nothing and leaves the reset token usable for a retry.

- **The password alone could remove TOTP.** On a TOTP-enrolled account, a session plus the password was enough to regenerate the recovery code, and a reset with that fresh code clears TOTP — so whoever held only the first factor could strip the second. `POST /auth/recovery-code/regenerate` now also requires a current TOTP `code` on an enrolled account, checked like `POST /auth/totp/disable` (counted in the per-account TOTP window, single-use). **Client change:** a client that regenerates on an enrolled account must send `code`; without it the request answers 401 `totp_invalid_code` (a missing code does not count against the TOTP window; a missing code on `POST /auth/totp/disable` no longer does either). Accounts without TOTP are unaffected.

- **A login could undo a concurrent password change.** On an account whose password hash predates the current bcrypt cost, a successful login re-hashes the password and saves it. That write replaced the hash unconditionally, so a login racing a password change could put the old password back. The upgrade now saves only while the stored hash is still the one the login verified; otherwise it is skipped.

- **A server restarted more often than its sweep interval never swept.** The lapsed-account and expired-rows sweeps first ran one interval after boot, so under the `24h` default a daily deploy reset the clock before either sweep ran, and lapsed accounts outlived their stated grace period. Both sweeps now first run ten minutes after boot (or one interval, if that is shorter), then every interval.

- **Foreign keys and the busy timeout lapsed after 30 minutes.** `foreign_keys`, `busy_timeout` and `journal_mode` were set by one `Exec` on the first pooled connection, but the pool retires a connection after 30 minutes and the replacement opened with SQLite's defaults: foreign keys off and no busy wait. From then on a write racing an account deletion or a lapsed-account purge could leave orphaned device, blob or recovery rows, and a write contending with the purge failed at once with `SQLITE_BUSY`. The pragmas now travel in the connection string, so the driver applies them to every connection it opens.

- **A client could choose its own rate-limit bucket behind a trusted proxy.** When every `X-Forwarded-For` hop was trusted — a NAT gateway inside the trusted range — the server fell back to `X-Real-IP`, which some proxies pass through from the client verbatim. `X-Real-IP` is no longer read; every `X-Forwarded-For` header line is considered, not just the first. An IPv6 client is now keyed by its /64 rather than its full address, since one subscriber routinely holds the whole /64. An unparseable hop such as a proxy's `unknown` now ends the walk instead of letting the client's own entries to its left become the key. `TRUSTED_PROXY_CIDRS` refuses an over-broad prefix at startup (a public IPv4 range wider than /12 or IPv6 wider than /32; a private, loopback, CGNAT or link-local range no wider than the range itself; so `0.0.0.0/0` and `::/0` fail) and unmaps IPv4-mapped entries, which previously never matched.

- **A stolen managed session could erase its account.** `DELETE /account` re-checks the current password, but a managed account has none, so a managed session alone was enough — and a bridge re-mint never revoked earlier ones, so a stolen token kept this power for the whole `SESSION_TTL`. `DELETE /account` now answers `403 managed_account_delete_via_bridge` for a managed session and changes nothing; a managed account is erased only through the bridge purge (`DELETE /managed/accounts/{account_id}`), which ovumcy-managed drives behind its own re-authentication. **Client note:** a managed client deletes the account through ovumcy-managed, never through this server's `DELETE /account`; the official app already does.

- **Rotating the recovery code left issued reset tokens valid.** Whoever held the old code could start a reset, wait for the owner to rotate, and still complete the reset — taking the account and clearing its 2FA — for the rest of the token's 30 minutes. Regeneration now deletes pending reset tokens; sessions are still left alone. Forgot-password writes its token only while the recovery-code hash it verified against is still current, so a request racing the rotation cannot slip a token in after the delete.

- **Changing the password left a pending TOTP login challenge valid.** A challenge minted by a login under the old password could still be completed with a code after the change, yielding a fresh session. Change-password now deletes pending challenges along with reset tokens.

- **A password over 72 bytes returned 500 and burned the reset token.** bcrypt refuses input past 72 bytes, and that error surfaced raw; 37 Cyrillic characters were enough. Register, change-password, and reset now reject such a password with their usual weak-password key, and reset checks it before consuming the token, so a rejected password leaves the token usable for a retry.

- **A TOTP enrollment started before a password change could still be completed.** Enrollment completion needs only a session, and a password change left a pending (not yet verified) secret in place, so whoever started an enrollment with the old password — and kept the secret — could later finish it from any session, take the recovery code that verify hands out and sign the owner's other sessions out. A password change now discards the pending secret in its transaction; an enrollment in progress must be restarted. An enrollment start verified against the old password that lands after the change writes nothing and answers `invalid_current_password`. An enabled factor is unaffected.

- **Removing a device left its sessions alive.** Sessions were scoped to the account only, so removing a lost or stolen device from the device list freed its slot but its session kept syncing for up to the full `SESSION_TTL`. A session is now bound to the device it attaches through `POST /sync/devices` (the first attach; a later one never moves it), and `DELETE /sync/devices/{device_id}` revokes every session bound to that device in the same transaction — removing your own device signs that client out. Sessions that existed before this release are bound on their client's next attach; until then a password change remains the way to cut them off. Requires running `migrate` (adds `sessions.device_id`).

- **Logging in again reset the TOTP guess budget.** Each login challenge allowed five wrong codes, and a new login replaced the challenge with a fresh one, so an attacker holding the password could cycle logins and keep guessing — roughly a one-in-five chance a day of landing a valid code. Code attempts are now also capped per account: 5 per fixed 15-minute window across every challenge, per client address and per account (a later change split this into three separate budgets of 5; see the TOTP-budget entry under Fixed), after which the challenge route answers 429 `rate_limited` with `Retry-After` at the window's end. A new login does not reset the count; a successful verify does. The attempt is reserved in one statement before the code is checked, so concurrent guesses cannot slip past the cap. Requires running `migrate` (adds `totp_failure_windows`).

- **Pre-authentication hardening.** Every session-authenticated route now passes a per-client-IP bucket before the session lookup, with a valid session refunding its slot, so a caller without a session can no longer drive store lookups unmetered. `POST /auth/totp/challenge` is rate-limited before it reports `503 totp_not_configured`. A JSON body followed by anything but whitespace — even `{}` or `null` — is now `400 invalid_json`. An invalid `FIELD_ENCRYPTION_KEY` no longer quotes the offending character of the key in the startup error. `purge-lapsed-accounts` no longer applies pending migrations as a side effect; it refuses and points at `migrate`.

- **`METRICS_ENABLED=true` now requires `METRICS_BEARER_TOKEN`.** An unauthenticated `/metrics` was one proxy rule away from public; the server now refuses to start with metrics on and no token.

- **Anyone could lock a known login out with no way back in.** The per-login ceiling counted every attempt, successful or not, and nothing cleared it, though the code claimed the recovery code was the unblock path: a reset did not touch the bucket, and the owner's next login was still `429`. A login that issues a session now refunds its slot, so only failures stay charged, and a successful `POST /auth/forgot-password` clears the login's bucket. A sustained flood of failures still blocks the login while it lasts.

- **A delayed managed-session mint could reverse an entitlement lapse.** `POST /managed/session` set `premium_active` and cleared `lapsed_at` on every call, so a mint that was retried or delivered late, after the lapse signal had already been applied, restored premium and returned a live session. A mint now never clears a lapse: on a lapsed account it answers `409 managed_account_lapsed` and issues nothing. The way back is the reactivation signal (`POST /managed/accounts/{account_id}/premium` with `active: true`), which now requires an `as_of` timestamp and is applied only when it is newer than the lapse. Lapse and reactivation signals are ordered by `as_of` (new column `entitlement_signal_as_of`, migration `0011`), so a stale signal answers `409 stale_entitlement_signal` and changes nothing. A lapse needs `as_of` too: one without it answers `400 invalid_entitlement_signal`, because a lapse ordered by this server's receive time could win over a later reactivation stamped by a managed clock that runs behind, and the account would be purged. **Bridge change:** a bridge that sends a lapse without `as_of` must add it; ovumcy-managed already does. The lapse write and its session revocation now share one transaction.

  `sync_enabled=false` is now enforced as well as reported: device, recovery-key and blob routes answer `403 sync_disabled` for a session whose account reports it. The mint's session insert also re-checks the lapse in the same statement: a lapse still in force when the insert runs refuses the mint (`409 managed_account_lapsed`), and one that commits after it revokes the new session. The managed service has to send the reactivation signal before minting for a resubscribed account; until it does, a lapsed account cannot sync again.

- **The log sanitizer missed two families of steering characters.** It stripped the C0 range and DEL, which closed line-break forgery and the `\x1b[` escape route, but left the C1 range and the Unicode format category untouched. A path arrives percent-decoded, so `%C2%9B` reached the log as U+009B — the single-character CSI a terminal acts on exactly like `\x1b[` — and `%E2%80%AE` reached it as a bidirectional override, which reorders how the rest of the entry is displayed without executing anything. Both are now stripped alongside the C0 range; printable text, including non-ASCII paths, is untouched.

- **Four routes reached the store with no rate limit at all.** `GET /auth/session`, `GET /sync/capabilities`, `GET /sync/devices`, and `DELETE /auth/session` were the only routes that could spend server work on a caller's behalf without passing a limiter, so a looping client or a captured session could drive session lookups and device queries at whatever rate the connection allowed. The three authenticated read-only routes now carry a per-account ceiling and `DELETE /auth/session` a per-client-IP one — the latter because it consumes the bearer token instead of authenticating through it, leaving no account identity to key on before the revoke. `openapi.yaml` records the added `429` on all four.

  The read ceiling is a fixed multiple of the existing `AUTH_RATE_LIMIT_COUNT` (300 per minute per account per route at the default) rather than a new knob, so there is still one rate-limit dial. It is deliberately far above any real client cadence: these routes are called on screen focus or an explicit tap, never on a timer, so the bound is reachable by a runaway loop and not by a person navigating an app.

  Decision (2026-07-28): `GET /healthz` and `GET /readyz` stay unlimited, now pinned by a regression test. A container healthcheck polls readiness on a fixed interval and an uptime monitor polls liveness on its own; throttling either would turn routine monitoring into a reported outage, with an orchestrator restarting or depooling a server that was answering correctly. `GET /metrics` (off by default, scraped on the collector's interval) and the `MANAGED_BRIDGE_TOKEN` machine-to-machine bridge routes (disabled by default, one first-party caller that may reconcile in bursts) stay unlimited for the same operator-facing reasons.

- **The container healthcheck now reports database health.** `HEALTHCHECK` probed `GET /healthz`, which answers from a constant and consults nothing, so a container whose database had become unreadable — deleted, corrupt, permission-locked — reported `healthy` to the runtime and to any orchestrator for as long as the HTTP loop kept accepting connections. It probes `GET /readyz` instead, which touches the store. `GET /healthz` is unchanged and stays the pure liveness answer for a proxy or uptime check.

- **The bundled Caddy edge collapsed every client into one rate-limit bucket.** `docker-compose.caddy.yml` set no `TRUSTED_PROXY_CIDRS`, so every request reached the server from Caddy's address and a few failed logins from anyone throttled auth for all users for the window. Caddy now sits at a fixed address on its own network (`SYNC_PROXY_IP` in `SYNC_EDGE_SUBNET`) and only that address is trusted.

- **Compose could not configure 2FA, sweeps, or timeouts.** `docker-compose.yml` hard-coded its environment and omitted `FIELD_ENCRYPTION_KEY`, `TOTP_ISSUER`, the sweep variables, and both HTTP timeouts, so the documented way to enable TOTP did not reach the container. Every configuration variable is now passed through from the shell or a `.env` file, with the server default when unset.

- **Docs drift.** The plain `docker run` quick start now prepares `./data` for the non-root image and binds loopback like Compose; the lint pin in `CONTRIBUTING.md` matches CI; `SECURITY.md` names the in-process lapse sweep, the recovery-then-re-enroll path after a key rotation, and all six asserted hardening headers; the proxy docs name the forwarded-IP headers.

## [0.3.0] - 2026-07-24

A major auth, security-hardening, and supply-chain release since `v0.2.0`: optional TOTP 2FA, account recovery and password management, authenticated account deletion, managed entitlement-lapse cleanup, in-process retention sweeps, signed release artifacts, and a substantially hardened CI and quality bar.

### Added

- **TOTP two-factor authentication.** Optional owner 2FA — enrollment, a login second-factor challenge, and disable — gated on `FIELD_ENCRYPTION_KEY`, with challenge metrics exposed for operators.
- **Account recovery and password management.** Password change, recovery codes, and recovery-code-based password reset across the auth surface.
- **Authenticated account deletion.** `DELETE /account` erases every row the server holds for an account in a single transaction.
- **`GET /auth/session`** exposing the current `totp_enabled` state.
- **Device management.** `GET /sync/devices` lists an account's attached devices and `DELETE /sync/devices/{device_id}` removes one (account-scoped, no IDOR), so reaching the device limit no longer forces deleting the whole account to free a slot.
- **Machine-readable OpenAPI 3.1 spec** (`openapi.yaml`) covering the full HTTP surface, plus a zero-knowledge boundary diagram in the README.
- **Entitlement-lapse cleanup for managed accounts.** New bridge endpoint `POST /managed/accounts/{account_id}/premium` lets the managed-auth service signal an entitlement lapse (`active: false`) or retract one (`active: true`); a new `purge-lapsed-accounts` CLI subcommand (`-dry-run`, `-limit`) erases a managed account's data once its lapse has exceeded the configurable `LAPSED_ACCOUNT_GRACE_PERIOD` (default 60 days). Self-hosted/community accounts are entirely unaffected — the lapse marker can only ever be set on a `mode=managed` account. See [docs/self-hosting.md](docs/self-hosting.md#entitlement-lapse-cleanup).
- **In-process lapsed-account sweep.** `serve` itself now erases lapsed managed accounts past the grace period, every `LAPSED_ACCOUNT_SWEEP_INTERVAL` (default `24h`, first run one interval after boot; `0` disables the in-process sweep and leaves `purge-lapsed-accounts` as the only trigger — the rollback lever), with `LAPSED_ACCOUNT_SWEEP_LIMIT` capping candidates per run (unset = the store's default page size). Both triggers are idempotent and safe to run together, so the documented retention window holds without an operator scheduling anything.
- **In-process expired-rows sweep.** `serve` now deletes expired sessions, password-reset tokens, and TOTP challenges every `EXPIRED_ROWS_SWEEP_INTERVAL` (default `24h`, first run one interval after boot; a non-positive value disables the sweep — the rollback lever), bounded by `EXPIRED_ROWS_SWEEP_LIMIT` rows per table per run (`0` = the store's own default page size). Expiry was already enforced at use time on every read path; these tables were simply never physically emptied and were the only ones still growing without bound.
- **Operator-tunable HTTP timeouts.** `HTTP_READ_TIMEOUT` (default `10s`) and `HTTP_WRITE_TIMEOUT` (default `15s`) expose the previously hardcoded per-request windows. Together with `MAX_BLOB_BYTES` they bound how slow a client may be while still moving a full-size blob — at the defaults a 16 MiB transfer needs roughly 1.7 MB/s — so deployments syncing large blobs over slow links can widen the windows without a fork. Zero and negative values are rejected: a zero `net/http` timeout means no timeout at all.

- **Relicensed** from AGPL-3.0 to the PolyForm Noncommercial License 1.0.0.
- **Runtime image switched to distroless** to drop the vulnerable gnutls chain.
- Tightened auth rate-limit ceilings.
- **Compose baseline now binds to loopback by default.** `docker-compose.yml` publishes the service on `127.0.0.1:8080` instead of all host interfaces; use a `docker-compose.override.yml` to publish on `0.0.0.0` for remote/LAN access.

### Fixed

- **Device limit could be exceeded under concurrency.** Attaching a device counted the account's devices and then inserted in two separate steps, so simultaneous attaches all passed the same check and overran `MAX_DEVICES`. The ceiling is now a predicate inside the insert statement (matching the blob-generation CAS), so concurrent attaches collapse to the limit. Re-attaching an already-owned device still refreshes its row without consuming a slot.
- **Explicit `LAPSED_ACCOUNT_SWEEP_LIMIT=0` no longer fails startup.** The documented "0 = the store's own default page size" held only for the unset case; an explicitly set `0` was rejected as non-positive. Only negative values are rejected now.
- **The `Authorization` scheme is case-insensitive.** `bearer <token>` and `BEARER <token>` now authenticate exactly like `Bearer <token>` (RFC 7235 §2.1); previously they were rejected with `401`.

### Security

- Reject the reserved `managed:` login prefix on public registration.
- Fail closed on login when a TOTP-enrolled account has no encryption key — no silent single-factor downgrade.
- Equalize bcrypt timing on `Login` and `ForgotPassword` early-return paths (CWE-208).
- Bound the in-memory auth rate-limiter map with an amortized sweep of expired entries, so a sustained distributed attempt can no longer grow it without limit; in-window entries are never evicted, preserving throttling.
- Raise the bcrypt cost for password and recovery-code hashes from 10 to 12, regenerate the timing-equalization placeholder at the same cost so CWE-208 login-enumeration parity holds, and transparently re-hash legacy cost-10 password hashes on the next successful login (best-effort; a failed re-hash never fails the login).
- Preserve the claimed TOTP step when enabling 2FA so an enrollment code can no longer be replayed within its skew window. The enable transition previously reset `totp_last_used_step` to 0, letting the just-verified enrollment code re-authenticate on the login-challenge and disable paths; the enable flip now touches only the enabled flag while a fresh enrollment still resets the step (RFC 6238 §5.2).
- Move blob generation-freshness into an atomic SQL compare-and-swap; make password-reset-token consumption atomic.
- Harden the TOTP login flow; annotate reviewed gosec findings (G202 in `DeleteAccount`, G505/G115 in TOTP).
- Pin both Dockerfile base images (`golang`, `distroless/static-debian12`) by digest instead of tag alone, kept current by Dependabot's weekly `docker` update.
- Sign the published container image. The `Docker Image` workflow signs the runtime image with keyless cosign and attaches SLSA build provenance. Verification steps are documented in [docs/self-hosting.md](docs/self-hosting.md).
- Recover from handler panics at the transport layer: a panic now returns a clean `500 internal_error` instead of a dropped connection, and is logged as a controlled, secret-free line (method + path only) rather than `net/http`'s default unbounded stack trace — keeping the no-secret-in-logs contract even on the failure path.
- Cap the accepted blob generation below the int64 ceiling. Without it, a client holding its own valid session could write `generation = math.MaxInt64` and permanently lock itself out of its own blob (the monotonic-generation CAS could never find a strictly-greater value). Owner-only self-lockout hardening surfaced by an adversarial audit; the client's millisecond-timestamp generation is astronomically far below the cap, so legitimate writes are unaffected.
- The entitlement-lapse signal immediately revokes every still-valid session on a lapsed managed account (no entitlement, no sync), independent of the data-retention grace period.
- The purge sweep re-checks the lapse marker and grace cutoff inside the same transaction as the deletion itself, so a session mint that races a scheduled sweep run always preserves the account intact.
- The rate-limit client IP is now canonicalized (IPv4-unmapped and IPv6 zone-stripped), so an IPv6 caller behind a trusted proxy can no longer mint distinct rate-limit buckets for one address by varying the zone in a forwarded header. Added native fuzz coverage for the client-IP parsers.
- **Per-account rate limit on sync reads.** `GET /sync/blob` and `GET /sync/recovery-key` now pass the same per-account limiter as their PUT counterparts: a valid session could previously drive unmetered reads of up to `MAX_BLOB_BYTES` ciphertext (plus the base64 encoding cost) past the per-IP auth gate. The budget is unchanged — `AUTH_RATE_LIMIT_COUNT` per `AUTH_RATE_LIMIT_WINDOW` per account, per endpoint.
